# Навантажувальне тестування (ЛР №4)

## 1. План тестування

### Інструмент

Обрано **Locust**.

- Сценарії пишуться звичайним Python-кодом, тією ж мовою, що й проєкт, тож поведінку користувача легко описати і зберігати в репозиторії поруч із кодом.
- Режим `--headless` зберігає метрики в CSV, з яких автоматично будуються таблиці та графіки звіту.
- Веб-інтерфейс (`http://localhost:8089`) показує графіки наживо, що зручно для демонстрації.
- Безкоштовний і не потребує Java (на відміну від JMeter) чи окремої мови сценаріїв (на відміну від k6 на JavaScript).

### Тестове середовище

| Параметр | Значення |
|---|---|
| Середовище | `sandbox` (`APP_ENV=sandbox`), окрема база `vet_crm_sandbox.db` |
| Сервер | `uvicorn app.main:app`, 1 воркер, без `--reload` |
| База даних | SQLite |
| Генератор навантаження | Locust на тій самій машині, що й сервер |

Скрипт `loadtest/run.py` перевіряє через `/health`, що сервер працює саме в sandbox, і відмовляється навантажувати production.

### Цільові ендпоінти MVP

| Ендпоінт | Хто викликає | Чому важливий |
|---|---|---|
| `GET /` (→ `/ui/`), `GET /ui/login.html` | відвідувач | перша сторінка, яку бачить кожен |
| `GET /health` | відвідувач, хостинг | перевірка стану сервісу |
| `POST /auth/register` | новий клієнт | хешування пароля + запис у БД |
| `POST /auth/login` | клієнт, адмін | перевірка пароля bcrypt + видача JWT |
| `GET /home`, `GET /users/me` | клієнт | домашня сторінка та профіль |
| `GET /pets`, `POST /pets` | клієнт | читання та запис тварин |
| `GET /appointments`, `POST /appointments` | клієнт | основна бізнес-операція: запис на прийом |
| `POST /appointments/{id}/cancel` | клієнт | зміна стану запису |
| `GET /ui/client.html` | клієнт | статична сторінка кабінету |
| `GET /admin/stats`, `GET /admin/users` | адмін | агрегуючі запити (необов'язково, див. нижче) |

### Сценарій поведінки користувача

Сценарій описаний у `loadtest/locustfile.py`. Суміш віртуальних користувачів відтворює аудиторію клініки.

**Клієнт (вага 6).** Реєструється з унікальним email, входить і додає тварину. Далі виконує дії з паузою 1–3 с між ними («час на роздуми»), обираючи дію відповідно до ваги:

| Дія | Вага |
|---|---:|
| Домашня сторінка `GET /home` | 4 |
| Список тварин `GET /pets` | 4 |
| Список записів `GET /appointments` | 3 |
| Профіль `GET /users/me` | 2 |
| Сторінка кабінету, додати тварину, записатися, скасувати запис | по 1 |

Якщо реєстрація чи вхід не вдалися тричі поспіль, віртуальний користувач зупиняється, щоб не створювати каскад вторинних помилок 401.

**Анонімний відвідувач (вага 2).** Відкриває головну, сторінку входу і `/health` з паузою 2–5 с.

**Адміністратор (вага 1).** Переглядає статистику, користувачів і всі записи. Бере участь лише тоді, коли задано змінні `LOADTEST_ADMIN_EMAIL` і `LOADTEST_ADMIN_PASSWORD`.

### Профілі навантаження

| Профіль | VUsers | Ramp-Up | Тривалість | Призначення |
|---|---|---|---|---|
| `baseline` (контрольний) | 50 | 5 корист./с → 10 с | 3 хв | типове навантаження, базові метрики |
| `step` (ступінчастий) | 10 → 25 → 50 → 100 → 150 | 5 корист./с на кожному ступені | 5 × 60 с = 5 хв | пошук точки деградації |

### Метрики та спосіб збору

| Метрика | Джерело |
|---|---|
| RPS (запити за секунду) | Locust, загальний і по кожному ендпоінту |
| Latency: середній, min, max, p50, p95, p99 | Locust |
| Error Rate | Locust: частка відповідей з помилкою (4xx/5xx або обірване з'єднання) |
| CPU і RAM сервера | `loadtest/monitor.py` (psutil) раз на секунду знімає показники процесу uvicorn і системи |

CPU процесу вимірюється у відсотках **одного ядра**: 100% означає, що процес повністю зайняв ядро.

## 2. Запуск

```bash
pip install -r requirements-loadtest.txt
```

**Термінал 1** — сервер sandbox без `--reload`:

```bash
uvicorn app.main:app
```

**Термінал 2** — тест:

```bash
python loadtest/run.py baseline     # контрольний запуск, ~3 хв
python loadtest/run.py step         # ступінчастий, ~5 хв
```

Щоб включити адміністраторів у суміш користувачів, перед запуском задайте змінні (пароль у код не потрапляє):

```bash
export LOADTEST_ADMIN_EMAIL=admin@example.com
export LOADTEST_ADMIN_PASSWORD='ваш_пароль'
```

Параметри профілів можна змінити, наприклад: `python loadtest/run.py baseline --users 100 --duration 300`.

Інтерактивний режим з графіками наживо: `locust -f loadtest/locustfile.py --host http://127.0.0.1:8000`, далі відкрийте http://localhost:8089.

## 4. Обмеження первинного тестування

- Locust і сервер працюють на одній машині й конкурують за CPU, тож абсолютні цифри нижчі, ніж були б на окремому сервері.
- SQLite і один воркер uvicorn — конфігурація sandbox. Production на PostgreSQL з кількома воркерами поводитиметься інакше, тому результати порівнюються між запусками, а не переносяться на production напряму.
- Кожен запуск додає в базу sandbox нових тестових користувачів. Перед повторним тестом базу можна видалити (`rm vet_crm_sandbox.db`), і вона створиться заново при старті сервера.

## 5. Висновки за результатами первинного тестування

**Тестове середовище:** MacBook (Apple Silicon, 10 ядер), sandbox, SQLite, 1 воркер uvicorn, Python 3.9.6.

| Метрика | baseline (50 VUsers) | step, 150 VUsers (стабільний режим) |
|---|---|---|
| RPS | 21.2 | 64.8 |
| Latency p50 | 7 мс | 4 мс |
| Latency p95 | 98 мс | 12 мс |
| Latency max | 6346 мс | 3800 мс (під час розгону) |
| Error Rate | 0.32% | 0.00% (усі 0.11% помилок тесту — під час розгонів) |
| CPU сервера (сер. / макс.) | 17% / 102% одного ядра | 26% / 103% одного ядра |
| RAM сервера | 77–78 МБ | 84 МБ |

Результати ступінчастого тесту за ступенями:

| VUsers | RPS | p50, мс | p95, мс | max p95 під час розгону, мс | Error Rate |
|---:|---:|---:|---:|---:|---:|
| 10 | 4.2 | 8 | 16 | 1300 | 0.00% |
| 25 | 10.9 | 8 | 15 | 1800 | 0.00% |
| 50 | 21.9 | 7 | 15 | 1800 | 0.00% |
| 100 | 43.1 | 5 | 14 | 3300 | 0.00% |
| 150 | 64.8 | 4 | 12 | 3800 | 0.00% |

**Пропускна здатність масштабується лінійно** (≈0.43 RPS на одного віртуального користувача) аж до 150 VUsers. Точку насичення в стабільному режимі не досягнуто: p95 тримається на рівні 12–16 мс на всіх ступенях, а середнє завантаження процесу сервера на 150 VUsers становить лише 26% одного ядра.

Загальний p95 за весь ступінчастий тест (1100 мс) значно вищий за p95 стабільного режиму (12–16 мс), бо підсумкова статистика включає п'ять періодів розгону.

### Перші вузькі місця

1. **Хешування паролів bcrypt блокує сервер.** Реєстрація (p95 ≈ 6 с) і вхід (p95 ≈ 2 с) — найповільніші операції. Хешування виконується синхронно всередині async-обробника, тож поки рахується хеш, сервер не обробляє інших запитів, і під час масових реєстрацій гальмують усі ендпоінти, навіть `GET /health` (max 300 мс замість типових 2 мс). Сплески затримки зростають разом із кількістю **одночасних** нових користувачів: 1.3 с при додаванні 10 VUsers, 3.8 с при додаванні 50 VUsers. Тобто систему обмежує не загальна кількість користувачів, а інтенсивність реєстрацій і входів.
2. **SQLite не витримує конкурентних записів.** Усі помилки 500 виникли лише на операціях запису (`POST /auth/register`, `POST /pets`) і лише в моменти розгону. Ймовірна причина — `database is locked`: SQLite допускає одного записувача, а поки цикл подій заблоковано хешуванням, відкрита транзакція не завершується і інші запити перевищують тайм-аут очікування.
3. **Обірвані з'єднання.** Частина запитів у ті самі моменти завершилась `ConnectionResetError`: сервер не встигав приймати нові з'єднання, поки цикл подій був зайнятий.
4. **Використовується лише одне ядро з 10.** Під час розгонів процес сервера впирається в 100% одного ядра, тоді як система загалом завантажена менше ніж на 50%. Один воркер uvicorn не може скористатися рештою ядер.

Пам'ять стабільна (71–84 МБ) і не зростає з часом — ознак витоку пам'яті немає.

### Рекомендації для наступного етапу

- Виконувати bcrypt у пулі потоків (`run_in_threadpool`), щоб хешування не блокувало цикл подій.
- Запускати uvicorn з кількома воркерами (`--workers N`), щоб використовувати всі ядра.
- Перейти на PostgreSQL, який підтримує паралельні записи.
- Повторити тестування на більшому навантаженні (300–500 VUsers) і з вищою швидкістю розгону, щоб знайти реальну межу пропускної здатності.
