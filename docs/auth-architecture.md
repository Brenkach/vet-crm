# Лабораторна робота №2: користувачі, ролі та розмежування доступу

## Структура

```
app/
  core/config.py      налаштування (pydantic-settings, змінні оточення / .env)
  core/security.py    хешування паролів (bcrypt) і JWT
  core/deps.py        залежності: get_current_user, require_roles, ensure_owner_or_admin
  db/database.py      async-рушій SQLAlchemy, сесія
  models.py           User, Pet, Appointment + enum Role, AppointmentStatus
  schemas.py          Pydantic-схеми запитів і відповідей
  api/                auth, users, home, pets, appointments, admin
  create_admin.py     консольне створення адміністратора
tests/                pytest: юніт- та інтеграційні тести
```

## Обґрунтування рішень

**База користувачів.** Таблиця `users` зберігає email (унікальний, індексований), ім'я, хеш пароля, роль і прапорець `is_active`. Пароль ніколи не зберігається у відкритому вигляді: використовується bcrypt із випадковою сіллю, бо це повільний, стійкий до перебору алгоритм.

**Ролі.** Роль зберігається як поле-enum (`admin`, `client`), а не окремою таблицею. Для двох-трьох фіксованих ролей це простіше і достатньо. Якщо в майбутньому з'являться гнучкі дозволи, модель можна розширити до таблиць `roles` / `permissions` без зміни API. Enum записується як рядок (`native_enum=False`), тож схема однаково працює в SQLite (тести) і PostgreSQL (docker-compose).

**Автентифікація через JWT.** Після входу клієнт отримує підписаний токен і передає його в заголовку `Authorization: Bearer`. Сервер не зберігає сесії (stateless), що добре масштабується і зручно для REST API та майбутнього фронтенду чи мобільного клієнта. У токені лише `sub` (id користувача) і термін дії; роль щоразу читається з БД, тому її зміна адміністратором діє одразу.

**Реєстрація.** Публічна реєстрація завжди створює роль `client`; поле `role` у запиті ігнорується. Адміністратор створюється тільки через консольну команду `python -m app.create_admin`, тобто людиною з доступом до сервера. Це закриває шлях самопризначення адмінських прав.

**Розмежування доступу через залежності FastAPI.** Уся логіка доступу зосереджена в `core/deps.py` і підключається декларативно:

- `get_current_user` — автентифікація; без токена або з невалідним токеном повертає **401**.
- `require_roles(Role.ADMIN)` — вертикальне розмежування; не та роль → **403**. Для адмін-панелі залежність навішена на весь роутер `/admin`, тож новий адмінський маршрут не можна випадково залишити відкритим.
- `ensure_owner_or_admin(user, owner_id)` — горизонтальне розмежування (захист від IDOR); доступ до чужої тварини, запису чи профілю → **403**. Власник нових сутностей береться з токена, а не з тіла запиту.

Неіснуючий ресурс повертає 404, наявний, але чужий — 403, як вимагає завдання.

**Асинхронний стек.** FastAPI + SQLAlchemy 2.0 async дозволяють обробляти багато запитів без блокування на I/O до БД.

## Бізнес-логіка MVP (ветклініка)

Клієнт реєструється, додає своїх тварин, записує їх на прийом (не в минулому), переглядає та скасовує свої записи. Адміністратор бачить усіх користувачів, змінює ролі (крім власної), бачить усі тварини і записи, змінює статус прийому (`completed`, `cancelled`) і переглядає статистику.

## Основні маршрути

| Метод | Шлях | Доступ |
|---|---|---|
| POST | /auth/register | усі |
| POST | /auth/login | усі |
| GET | /home, /home/client, /home/admin | авторизовані / за роллю |
| GET, PATCH | /users/me, /users/{id} | власник або адмін |
| GET, POST, PATCH, DELETE | /pets, /pets/{id} | власник або адмін |
| GET, POST | /appointments, /appointments/{id}/cancel | власник або адмін |
| PATCH | /appointments/{id}/status | адмін |
| GET, PATCH | /admin/users, /admin/users/{id}/role, /admin/stats | адмін |

## Запуск

```bash
pip install -r requirements.txt
python -m app.create_admin --email admin@example.com --name "Admin"
uvicorn app.main:app --reload     # документація: http://127.0.0.1:8000/docs
pytest -v
```

За замовчуванням використовується SQLite (`vet_crm.db`). Для PostgreSQL задайте в `.env`:
`DATABASE_URL=postgresql+asyncpg://user:password@localhost:5432/vet_crm` і `SECRET_KEY=<довгий випадковий рядок>`.

## Тести (48 шт.)

- `test_security.py` — юніт-тести хешування та JWT (підробка й прострочення токена).
- `test_auth.py` — анонімний доступ (401), реєстрація, успішний вхід (200), помилки входу (401).
- `test_roles.py` — клієнт в адмін-панелі (403), адмін (200), заборона самопідвищення.
- `test_idor.py` — спроби змінити чужий профіль, тварину, запис (403).
- `test_business.py` — сценарії бізнес-логіки.

Кожен тест працює з окремою БД у пам'яті через підміну залежності `get_session`, тому тести незалежні й не чіпають робочу базу.
