# Балансування навантаження за допомогою Nginx (ЛР №6)

## Архітектура

```
                    клієнт (браузер, Locust, curl)
                               │  http://localhost  (порт HTTP_PORT, за замовчуванням 80)
┌──────────────────────────────┼─────────────────────────────────────────────┐
│ Docker              мережа frontend                                        │
│                     ┌────────┴────────┐                                    │
│                     │      nginx      │  єдина точка входу,                │
│                     │ (load balancer) │  upstream vet_crm_backend          │
│                     └────────┬────────┘                                    │
│             ┌────────────────┼────────────────┐   мережа backend          │
│             ▼                ▼                ▼   (internal)              │
│       ┌──────────┐     ┌──────────┐     ┌──────────┐                       │
│       │  app-1   │     │  app-2   │     │  app-3   │  однакові репліки     │
│       └────┬─────┘     └────┬─────┘     └────┬─────┘  (deploy.replicas: 3) │
│            └────────────────┼────────────────┘                             │
│                       ┌─────┴─────┐                                        │
│                       │    db     │  PostgreSQL + том postgres_data        │
│                       └───────────┘                                        │
└────────────────────────────────────────────────────────────────────────────┘
```

Назовні опублікований лише порт Nginx. Репліки застосунку і база даних доступні тільки у внутрішній мережі `backend`, тож обійти балансувальник неможливо.

| Файл | Призначення |
|---|---|
| `docker-compose.yml` | сервіси `db`, `app` (3 репліки), `nginx` |
| `nginx/Dockerfile` | образ балансувальника на основі `nginx:1.28-alpine` |
| `nginx/templates/default.conf.template` | конфігурація Nginx: `upstream` і `server` |
| `nginx/05-lb-algorithm.envsh` | вибір алгоритму за змінною `LB_ALGORITHM` |
| `loadtest/lb_check.py` | серія запитів і статистика: яка репліка що обробила |
| `loadtest/compare.py` | порівняння навантажувальних тестів |

## 1. Репліки застосунку

### Розгортання

У `docker-compose.yml` сервіс `app` має параметр:

```yaml
deploy:
  replicas: ${APP_REPLICAS:-3}
```

Docker Compose створює три однакові контейнери з одного образу: `vet-crm-app-1`, `vet-crm-app-2`, `vet-crm-app-3`. Кількість можна змінити без редагування файлу: `docker compose up -d --scale app=5`.

Усі репліки працюють з однією базою PostgreSQL, тому користувач, який зареєструвався через одну репліку, може увійти через іншу. Застосунок не зберігає стану в пам'яті: автентифікація через JWT, а всі дані лежать у БД. Саме це дозволяє масштабувати його горизонтально.

### Одночасний старт кількох реплік

Усі репліки стартують одночасно, і кожна запускає міграції та створює адміністратора. Щоб не було конфліктів:

- **Міграції** (`migrations/env.py`) беруть блокування PostgreSQL `pg_advisory_xact_lock`. Репліки проходять його по одній: перша оновлює схему, решта бачать, що схема вже актуальна, і нічого не роблять.
- **Створення адміністратора** (`app/core/bootstrap.py`): якщо дві репліки намагаються створити його одночасно, друга отримує помилку унікальності email, тихо відкочує транзакцію і продовжує роботу.

### Ідентифікація репліки

Кожна відповідь показує, хто її обробив:

| Де | Що | Хто додає |
|---|---|---|
| тіло `GET /health` | `"instance": "3f2a9c1b7d4e"` | застосунок |
| заголовок `X-Instance` у **кожній** відповіді | hostname контейнера | застосунок (middleware в `app/main.py`) |
| заголовок `X-Upstream-Addr` | IP-адреса і порт репліки, напр. `172.20.0.4:8000` | Nginx |

У Docker hostname контейнера — це його короткий ID. Відповідність ID і назви контейнера показує команда `docker ps`.

```bash
curl -i http://localhost/health
```

```
HTTP/1.1 200 OK
x-instance: 3f2a9c1b7d4e
X-Upstream-Addr: 172.20.0.4:8000

{"status":"ok","environment":"production","instance":"3f2a9c1b7d4e"}
```

## 2. Nginx як балансувальник

Конфігурація (`nginx/templates/default.conf.template`, скорочено):

```nginx
resolver 127.0.0.11 valid=5s ipv6=off;          # вбудований DNS Docker

upstream vet_crm_backend {
    zone vet_crm_backend 64k;
    # тут підставляється алгоритм: нічого (round robin), least_conn; або ip_hash;
    server app:8000 resolve max_fails=1 fail_timeout=10s;
    keepalive 16;
}

server {
    listen 80;

    location / {
        proxy_pass http://vet_crm_backend;
        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_connect_timeout 2s;
        add_header X-Upstream-Addr $upstream_addr always;
        # + заголовки Host, X-Real-IP, X-Forwarded-For, X-Forwarded-Proto
    }
}
```

**Блок `upstream`** — група серверів, між якими розподіляються запити. Замість переліку адрес використано ім'я сервісу `app`: вбудований DNS Docker повертає на нього IP-адреси **всіх** запущених реплік. Параметр `resolve` (відкрита версія Nginx з 1.27.3) змушує Nginx перевіряти цей список кожні 5 секунд. Тому при `--scale app=5` нові репліки підхоплюються автоматично, а зупинені зникають з балансування.

**Блок `server`** приймає трафік на порту 80 і через `proxy_pass` передає його групі `vet_crm_backend`. Заголовки `X-Real-IP` і `X-Forwarded-For` зберігають справжню адресу клієнта, бо інакше застосунок бачив би лише адресу Nginx.

**`keepalive 16`** тримає відкриті з'єднання до реплік, щоб не встановлювати нове TCP-з'єднання на кожен запит.

## 3. Round Robin

Round Robin — алгоритм Nginx за замовчуванням: запити передаються репліками по черзі, 1 → 2 → 3 → 1 → 2 → 3…

```bash
python loadtest/lb_check.py -n 12
```

Приклад виводу:

```
   №  Репліка (X-Instance)   Upstream (Nginx)         Статус  Час, мс
   1  3f2a9c1b7d4e           172.20.0.4:8000          200          12
   2  8b1e0d5a2c7f           172.20.0.5:8000          200           3
   3  c94d7e2f1a08           172.20.0.6:8000          200           2
   4  3f2a9c1b7d4e           172.20.0.4:8000          200           2
   5  8b1e0d5a2c7f           172.20.0.5:8000          200           2
   6  c94d7e2f1a08           172.20.0.6:8000          200           2
   ...

Розподіл запитів між репліками:
  3f2a9c1b7d4e      4   33.3%  ████
  8b1e0d5a2c7f      4   33.3%  ████
  c94d7e2f1a08      4   33.3%  ████
```

Кожна репліка отримала рівно третину запитів, і вони чергуються строго по колу. У лозі Nginx (`docker compose logs nginx`) видно те саме: кожен рядок має формат `клієнт -> адреса_репліки [статус] "запит"`.

## 4. Відмовостійкість

### Як Nginx виявляє непрацюючу репліку

Відкрита версія Nginx не має активних перевірок здоров'я (вони є лише в комерційній Nginx Plus), тому використано три механізми, які доповнюють один одного:

1. **Пасивна перевірка** (`max_fails=1 fail_timeout=10s`). Якщо запит до репліки завершився помилкою з'єднання або тайм-аутом, Nginx виключає її з ротації на 10 секунд, а потім обережно пробує знову.
2. **Прозорий повтор** (`proxy_next_upstream`). Запит, який не вдалося передати репліці, Nginx одразу повторює на наступній. Користувач отримує 200, а не помилку. `proxy_connect_timeout 2s` не дає довго чекати на мертву репліку.
3. **Оновлення списку через DNS** (`resolve`). Зупинений контейнер зникає з DNS Docker, і в межах 5 секунд Nginx прибирає його з групи. Коли контейнер повертається, Nginx додає його назад.

Крім того, кожна репліка має Docker `HEALTHCHECK` (`GET /health`), і Nginx стартує лише після того, як усі репліки стали `healthy` (`depends_on: condition: service_healthy`).

### Демонстрація

**Термінал 1** — безперервні запити:

```bash
python loadtest/lb_check.py --watch
```

**Термінал 2** — «зламати» одну репліку:

```bash
docker stop vet-crm-app-2
```

У першому терміналі видно:

```
  31  3f2a9c1b7d4e           172.20.0.4:8000                    200      2
  32  c94d7e2f1a08           172.20.0.5:8000, 172.20.0.6:8000   200   2004
  33  3f2a9c1b7d4e           172.20.0.4:8000                    200      2
  34  c94d7e2f1a08           172.20.0.6:8000                    200      2
```

Запит №32 найпоказовіший. У `Upstream` дві адреси: Nginx спробував мертву репліку, не дочекався з'єднання за 2 с, переслав запит на наступну і повернув користувачу 200. Далі трафік ділиться лише між двома здоровими репліками, без жодної помилки.

Повернути репліку:

```bash
docker start vet-crm-app-2
```

Приблизно через 10–15 секунд (стан `healthy` + оновлення DNS + `fail_timeout`) вона знову з'являється в ротації. Натисніть **Ctrl + C** у першому терміналі, щоб побачити підсумковий розподіл.

## 5. Альтернативні алгоритми

Алгоритм задається змінною `LB_ALGORITHM` у `.env` або прямо в команді:

```bash
LB_ALGORITHM=least_conn docker compose up -d nginx
LB_ALGORITHM=ip_hash docker compose up -d nginx
docker compose up -d nginx            # повернутися до round robin
```

Перезапускається лише контейнер Nginx: репліки і база продовжують працювати. Скрипт `nginx/05-lb-algorithm.envsh` підставляє потрібну директиву в блок `upstream`. Перевірити, що застосувалося: `docker compose logs nginx | grep Балансування`.

| Алгоритм | Як працює | Результат `lb_check.py -n 9` | Коли доречний |
|---|---|---|---|
| `round_robin` | по черзі | 3 / 3 / 3 | однакові репліки, короткі однорідні запити |
| `least_conn` | на репліку з найменшою кількістю активних з'єднань | 3 / 3 / 3 | запити різної тривалості: довгий запит (реєстрація з bcrypt) не блокує чергу на одній репліці |
| `ip_hash` | хеш IP клієнта визначає репліку | 9 / 0 / 0 — усі на одну | «липкі сесії»: дані сесії в пам'яті репліки, локальний кеш |

Чому `least_conn` на послідовних запитах виглядає як round robin: `lb_check.py` надсилає наступний запит лише після відповіді на попередній, тож у момент вибору в усіх реплік 0 активних з'єднань, і Nginx розв'язує нічию по черзі. Різниця з'являється під навантаженням, коли запити виконуються одночасно і мають різну тривалість. Найкраще її видно в навантажувальному тесті.

Чому `ip_hash` відправляє все на одну репліку: усі запити йдуть з одного комп'ютера, тобто з однієї IP-адреси. Нашому застосунку «липкі сесії» не потрібні, бо JWT і дані в БД роблять репліки взаємозамінними, тому для нас `ip_hash` невигідний: він позбавляє рівномірного розподілу.

Зважений Round Robin (`weight=N`) потребує окремого рядка `server` для кожного сервера. Він корисний, коли сервери мають різну потужність. У нас репліки однакові й описані одним іменем сервісу, тому ваги не застосовуються.

## 6. Порівняльне навантажувальне тестування

Порівнюємо одну репліку і три репліки за тим самим Nginx, тож різниця пояснюється лише кількістю реплік. Тест запускається в окремому проєкті `vet-crm-loadtest` у режимі sandbox, щоб тестові користувачі не потрапили в основну базу.

```bash
pip install -r requirements-loadtest.txt
docker compose down                     # звільнити порт 80

# 1 репліка
APP_ENV=sandbox docker compose -p vet-crm-loadtest up -d --build --wait --scale app=1
python loadtest/run.py baseline --host http://localhost --users 300 --spawn-rate 20 --duration 180 --name lb-1-replica

# 3 репліки (Nginx підхопить нові репліки сам)
APP_ENV=sandbox docker compose -p vet-crm-loadtest up -d --wait --scale app=3
python loadtest/run.py baseline --host http://localhost --users 300 --spawn-rate 20 --duration 180 --name lb-3-replicas

# порівняння
python loadtest/compare.py lb-1-replica lb-3-replicas

# прибрати тестове оточення разом з його базою
APP_ENV=sandbox docker compose -p vet-crm-loadtest down -v
docker compose up -d                    # повернути основну систему
```

Під час тестів у сусідньому терміналі видно завантаження кожного контейнера: `docker stats`.

**Чому 300 користувачів, а не 50, як у ЛР №4.** У ЛР №4 одна репліка на 150 користувачах використовувала в середньому лише чверть ядра, тобто ще не була перевантажена. Порівнювати масштабування має сенс лише тоді, коли одна репліка не встигає. Найважча частина сценарію — 300 реєстрацій з хешуванням bcrypt за 15 секунд розгону.

Результати: `loadtest/results/comparison.md` (таблиця і графіки), детальні звіти — у `loadtest/results/lb-1-replica/` і `loadtest/results/lb-3-replicas/`.

**На що дивитися.** У ЛР №4 головним вузьким місцем було хешування bcrypt: поки одна репліка рахує хеш, вона не обробляє інших запитів. З трьома репліками хешування йде паралельно на трьох ядрах, тож мають зменшитися p95, пік p95 під час розгону і p95 реєстрації/входу. RPS зростає лише тоді, коли одна репліка не встигала обробляти потік запитів, адже віртуальні користувачі роблять паузи 1–3 с між діями і не генерують запитів більше, ніж потрібно.

## Автоматична перевірка в CI

Job «Docker» у `.github/workflows/ci.yml` при кожному пуші перевіряє на справжньому Docker:

1. система піднімається (`docker compose up --build --wait`): Nginx, 3 репліки, PostgreSQL;
2. Round Robin: 12 запитів рівно розподіляються між 3 репліками;
3. після `docker stop vet-crm-app-2` усі запити успішні й обробляються 2 репліками;
4. після `docker start` репліка повертається в ротацію;
5. `ip_hash` відправляє всі запити на 1 репліку, `least_conn` використовує всі 3;
6. дані зберігаються після перезапуску всіх контейнерів.

## Результати

**Середовище:** MacBook (Apple Silicon, 10 ядер), Docker Desktop, Nginx 1.28, 3 репліки застосунку (1 воркер uvicorn у кожній), PostgreSQL 16.

### Round Robin (12 послідовних запитів)

| ID контейнера (`X-Instance`) | Контейнер | Адреса | Запитів |
|---|---|---|---:|
| `367956acc130` | vet-crm-app-2 | 172.22.0.5:8000 | 4 (33.3%) |
| `48aa258ab9cf` | vet-crm-app-3 | 172.22.0.3:8000 | 4 (33.3%) |
| `4307d18f0e87` | vet-crm-app-1 | 172.22.0.4:8000 | 4 (33.3%) |

Запити чергувалися строго по колу: app-2 → app-3 → app-1 → app-2 → … Помилок 0.

### Відмова репліки

Під час безперервних запитів (`lb_check.py --watch`) контейнер `vet-crm-app-2` було зупинено командою `docker stop`.

```
  62  48aa258ab9cf           172.22.0.3:8000                    200      6
  63  4307d18f0e87           172.22.0.4:8000                    200      7
  64  ?                      172.22.0.5:8000, vet_crm_backend   502   2008
  65  48aa258ab9cf           172.22.0.3:8000                    200      3
  66  4307d18f0e87           172.22.0.4:8000                    200      4
  67  48aa258ab9cf           172.22.0.3:8000                    200      4
```

Лог Nginx для запиту №64 (з'єднання `*278`):

```
[error] *278 upstream timed out (110: Operation timed out) while connecting to upstream, upstream: "http://172.22.0.5:8000/health"
[warn]  *278 upstream server temporarily disabled while connecting to upstream, upstream: "http://172.22.0.5:8000/health"
[error] *278 no live upstreams while connecting to upstream, upstream: "http://vet_crm_backend/health"
```

1. Nginx 2 секунди намагався з'єднатися з зупиненою app-2 (`proxy_connect_timeout 2s`).
2. Спрацювала пасивна перевірка: після першої невдачі (`max_fails=1`) репліку виключено з ротації (`temporarily disabled`).
3. Повторити запит на іншій репліці не вдалося: за ці 2 секунди DNS Docker прибрав зупинений контейнер, Nginx оновив список реплік (`resolve`), а повтор у межах групи, яка змінилася посеред запиту, Nginx не виконує. Тому цей запит отримав 502.

Усі наступні запити оброблялися лише здоровими app-1 і app-3 без помилок. Після `docker start vet-crm-app-2` репліка автоматично повернулася в ротацію.

**Висновок:** Nginx виявив непрацюючу репліку за першим невдалим запитом і виключив її з маршрутизації. Під час переходу один запит отримав помилку, бо збіглися тайм-аут з'єднання і оновлення списку реплік. Це обмеження пасивних перевірок відкритої версії Nginx: вона дізнається про відмову лише з невдалого запиту. Активні перевірки, які заздалегідь опитують сервери, є в Nginx Plus. Скоротити вікно можна меншим `proxy_connect_timeout`.

### Альтернативні алгоритми (9 послідовних запитів)

| Алгоритм | app-1 | app-2 | app-3 | Пояснення |
|---|---:|---:|---:|---|
| `round_robin` | 3 | 3 | 3 | по черзі |
| `ip_hash` | 0 | 9 | 0 | усі запити з однієї IP-адреси (`192.168.65.1`) → завжди та сама репліка |

### Порівняльне навантажувальне тестування: 1 репліка проти 3

Профіль: 300 віртуальних користувачів, розгін 20 корист./с (Ramp-Up 15 с), 180 с, сценарій з ЛР №4, обидва прогони через той самий Nginx, середовище sandbox.

### Висновки

1. **Одна репліка перевантажена.** 300 одночасних реєстрацій з хешуванням bcrypt повністю зайняли її єдине ядро. Оскільки bcrypt виконується синхронно і блокує цикл подій, гальмували **всі** запити: навіть простий `GET /pets` мав p95 5.8 с. Частина запитів чекала довше за `proxy_read_timeout 30s`, тому Nginx повертав помилку тайм-ауту. Звідси максимум рівно ~30 000 мс і Error Rate 2.14%.
2. **Три репліки розподілили навантаження.** Хешування йде паралельно на трьох ядрах, звичайні запити не застрягають за ним: p95 `GET /pets` впав з 5800 до 9 мс, а `POST /appointments` — з 1200 до 12 мс. Помилки практично зникли (0.01%).
3. **Пропускна здатність зросла на 62%.** Віртуальні користувачі чекають на відповідь перед наступною дією, тому коли сервер швидший, вони встигають зробити більше дій. Зростання менше за 3×, бо сценарій має паузи 1–3 с між діями, і на третину часу тесту припадав розгін з реєстраціями.
4. **Вузьке місце, знайдене в ЛР №4, залишилося.** Вхід і реєстрація все ще мають p95 близько 20 с: 300 реєстрацій за 15 секунд — це сотні хешувань bcrypt, і навіть три ядра не встигають. Горизонтальне масштабування зменшило проблему, але не прибрало її причину. Наступний крок — виконувати bcrypt у пулі потоків (`run_in_threadpool`), щоб хешування не блокувало обробку інших запитів, і запускати кілька воркерів uvicorn у кожній репліці.

Загалом балансування дало саме той ефект, заради якого впроваджується: система витримує більше навантаження, швидше відповідає, а відмова однієї репліки не зупиняє сервіс.
